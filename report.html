Summary

Users said the API was "unreliable and sometimes inaccessible". I found two separate stories behind that sentence.

The API was inaccessible because nginx was forwarding to the wrong port, and because the API process crashed whenever Postgres restarted and nothing brought it back.

It was unreliable because every dependency problem turned into a user-facing failure. A frozen database meant a 60-second hang. A stopped Redis meant a 500 after almost a minute, even though Redis isn't needed to answer the request. And nothing in the stack knew whether a service was actually healthy, only whether its container was running.

All six issues below are fixed, and each one was reproduced before the fix and re-tested after it, using the same steps both times. Everything was tested on a local single-instance stack. I haven't load-tested it, so this report shows correct failure behaviour, not capacity.

How I diagnosed them

I started from the wording of the complaint. "Inaccessible" means requests don't get through. "Sometimes" means it depends on conditions. "Unreliable" means it works, but not consistently. Any cause I found had to explain all three words, and that's why I didn't stop at the first bug.

Then I drew the request path: browser → nginx → API → Postgres, with a side branch API → Redis. Every arrow is a dependency, and dependencies fail in a small number of ways: the address is wrong, the service is gone, it's there but frozen, or it isn't ready yet. I went through each arrow with those four questions, read the code asking "what happens when this call fails?", and then forced each failure with Docker (restart, pause, stop) to see what users would actually get.

1. Wrong upstream port

The first thing I did was call the API through nginx:

text> curl.exe -i http://localhost:8080/api/users
HTTP/1.1 502 Bad Gateway
Server: nginx/1.25.5

The Server: nginx header told me the error came from nginx itself, so the request never reached the application. All four containers showed Up in docker compose ps, which already said something important: container status was not telling the truth about health. The nginx error log gave the actual reason:

textconnect() failed (111: Connection refused) while connecting to upstream,
upstream: "http://172.23.0.4:3001/api/users"

The API container is reachable, but nothing listens on 3001. default.conf has proxy_pass http://api:3001;, while index.js ends with app.listen(3000).

This explains "inaccessible", but a wrong port fails on every request, not "sometimes". So I kept going.

2. API crashes when Postgres restarts

Reading index.js, I noticed the pg connection pool had no error listener. The pool keeps idle connections open for about 10 seconds after a request. If the database drops them, for example during a restart or failover, the pool emits an error event, and in Node an unhandled error event kills the process.

To test it, I made one request so the pool held an idle connection, then restarted Postgres straight away:

powershellcurl.exe -s http://localhost:8080/api/users; docker compose restart postgres

Postgres was back within seconds. The API wasn't:

textproblem3-api-1   ...   Exited (1) 3 minutes ago

error: terminating connection due to administrator command
Emitted 'error' event on BoundPool instance at:
    at Client.idleListener (/app/node_modules/pg-pool/index.js:62:10)

The first line is Postgres politely telling its clients it's shutting down. The second is Node saying the pool raised an error and nobody was listening. With no restart: policy, the API stayed dead and nginx returned 502 until someone noticed.

This is the "sometimes". It only happens if someone used the API in the ~10 seconds before the database blip. Most of the time a restart goes unnoticed, and occasionally it takes the whole API down.

3. No timeouts on database calls

The other kind of database failure is when it doesn't go away cleanly but just stops answering, for example during a network partition, an overloaded host, or a stuck disk. I simulated that by freezing the Postgres container:

powershelldocker compose pause postgres; curl.exe -s -o NUL -w "%{http_code} after %{time_total}s\n" http://localhost:8080/api/users; docker compose unpause postgres
text504 after 60.002646s

60 seconds is exactly nginx's default proxy_read_timeout. The API had no limit of its own and would have waited forever, so nginx gave up first. While a request waits like that, it holds one of the pool's 10 connections. I only sent one request, but by reasoning, a burst of traffic during a slowdown would use up the pool and block healthy requests too.

I also found a related bug while reading the code. db.release() came after db.query() inside the try block, so a failed query never gave its connection back. Before, that was hard to trigger. Once I added a query timeout, every timeout would have leaked a connection, so the two had to be fixed together.

4. Redis on the critical path

The route ends with await redis.set("last_call", Date.now()) before sending the response. Nothing reads last_call back, so the user's response doesn't need this write, but it still waits for it. I stopped Redis and called the API:

text{"ok":false,"error":"Reached the max retries per request limit (which is 20)..."}
=> 500 after 56.583985s

Postgres was healthy and the query had already succeeded, but because of a bookkeeping write, the user waited almost a minute and got an error.

5. No health or readiness anywhere

docker-compose.yml had no healthchecks, no restart policies, and depends_on without a condition. depends_on only waits for a container to start, not for the service inside to be ready. So after a fresh deploy or a host reboot, the API can receive traffic before Postgres accepts connections. I didn't measure this race on the original stack; it comes from reading the config. What I did see directly was finding 1: all containers Up while 100% of API calls failed.

6. Homepage downloads as a file

Opening http://localhost:8080 in a browser downloaded a file. curl -i showed Content-Type: application/octet-stream. The location = / block uses return 200 "...", and a return has no file extension for nginx to infer a type from, so it falls back to default_type, which is application/octet-stream in the stock nginx.conf. The repo's own nginx/nginx.conf is empty and never mounted (compose only mounts conf.d), so the image's built-in one is in effect. This is cosmetic, but it's the first thing a person sees.

The fixes I applied

I kept every fix as small as possible and changed only three files.

nginx (nginx/conf.d/default.conf): the correct upstream port, and an explicit content type for the root response.

nginxlocation = / {
    default_type text/plain;
    return 200 "Welcome to the platform\n";
}

location /api/ {
    proxy_pass http://api:3000;
}

I left proxy_pass without a trailing slash on purpose, so the /api/users path is passed through unchanged, which is what Express expects.

API (api/src/index.js):

jsconst pool = new Pool({
  // ...existing settings
  connectionTimeoutMillis: 2000,
  query_timeout: 5000,
});

pool.on("error", (err) => {
  console.error("Postgres idle client error:", err.message);
});

const redis = new Redis({
  host: process.env.REDIS_HOST,
  port: 6379,
  maxRetriesPerRequest: 1,
});

redis.on("error", (err) => {
  console.error("Redis error:", err.message);
});

app.get("/api/users", async (req, res) => {
  try {
    const result = await pool.query("SELECT NOW()");

    redis.set("last_call", Date.now()).catch((err) => {
      console.error("Redis write failed:", err.message);
    });

    res.json({ ok: true, time: result.rows[0] });
  } catch (err) {
    console.error(err);
    res.status(500).json({ ok: false, error: err.message });
  }
});

Here's the reasoning behind each change:

  • pool.on("error") is the actual fix for the crash. The pool already discards the broken connection by itself; the listener just stops Node from treating that as fatal. The next request opens a fresh connection.
  • The timeouts make a stalled database fail in 2 seconds (can't get a connection) or 5 seconds (query stuck), not 60. SELECT NOW() normally takes a few milliseconds, so those limits leave plenty of headroom and still fail well before nginx's timeout. The user gets a clear error quickly, and the connection isn't held hostage.
  • pool.query() replaces the manual connect() / query() / release() sequence. It always returns the connection to the pool, including on error, which removes the leak entirely.
  • The Redis write is fire-and-forget with its own .catch, so a Redis problem is logged but never affects the response. maxRetriesPerRequest: 1 stops failed writes piling up in memory while Redis is down. I'd normally check with the product owner that last_call really is non-essential before making this change. Here, nothing reads it.

Compose (docker-compose.yml): healthchecks, readiness-based depends_on, and restart: unless-stopped on every service.

yaml  api:
    # build and environment unchanged
    restart: unless-stopped
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "-e", "require('http').get('http://127.0.0.1:3000/status', (r) => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
      interval: 10s
      timeout: 3s
      retries: 3

Postgres uses pg_isready, Redis uses redis-cli ping, and nginx now waits for the API to be healthy before starting.

I made two deliberate choices in the API healthcheck.

First, it calls /status, which doesn't touch the database. If the check depended on Postgres, a database outage would mark the API unhealthy too. On an orchestrator that restarts unhealthy containers, that turns one outage into a restart storm. The API process can be healthy while a dependency isn't; the timeouts above handle that case.

Second, it uses Node's own HTTP client, not wget. Busybox wget doesn't respect no_proxy, so in any environment that injects proxy variables into containers (my machine does), the check went out to the proxy and failed. The node -e version needs nothing that isn't already in the image.

The restart policy is a safety net, not the fix. If I'd only added restart: unless-stopped, the API would crash and come back on every database blip, failing requests each time, and the crash would be invisible. That's why the error handler is the real fix, and why I want restarts to be alerted on (see below).

Monitoring and alerts I would add

All six problems have one thing in common: the system failed silently. Containers stayed Up while users got errors. So I'd monitor from the user's side first, and use internal signals only to explain why something is failing.

Alerts that page someone. These are symptoms users feel, and they fire regardless of cause:

  • Synthetic check: GET /api/users through the public endpoint every minute, from outside the stack. Page after 3 consecutive failures. This would have caught finding 1 within minutes, even at 3am with no traffic.
  • 5xx rate on /api/ from nginx access logs: page if it stays above 5% for 5 minutes. This covers findings 2, 3 and 4.

Warnings that create a ticket, not a page. These are early signs:

  • p99 latency on /api/ above 1 second for 10 minutes. Requests now fail at 2 to 5 seconds instead of hanging, so slowly rising latency is an early warning before users see errors.
  • Container restarts above 3 in an hour. This one matters because of the restart policy I added. Without it, a crash loop would be hidden by automatic restarts.
  • Any container unhealthy for more than 2 minutes.

Dashboards, no alerts. These are the cause signals the on-call engineer checks once an alert fires:

  • Postgres connections in use, against the pool limit (10 per API instance) and the server's max_connections.
  • Counts of the new log lines: Postgres idle client error, Redis write failed, and timeout errors. A rise in any of these explains a 5xx spike before anyone opens a shell.
  • nginx upstream errors (connect() failed, upstream timed out).

Deliberately no alert on the homepage content type. A synthetic assertion on the header is enough; it's cosmetic and shouldn't wake anyone up.

For tooling I'd use whatever the platform already has, for example a blackbox exporter and nginx log metrics into Prometheus/Grafana, or CloudWatch Synthetics and Container Insights on AWS. The signals above matter more than the tool.

How I would prevent this in production

Every bug here passed the checks that existed. nginx -t said the config was valid, and the containers started. What was missing was anyone testing the system as a whole, and testing what happens when its dependencies fail. So prevention for me comes down to three things.

1. Test the system end to end before it ships. A CI job runs docker compose up, waits for healthy, then asserts that /api/users returns 200 with JSON and / returns text/plain. That takes under a minute and catches findings 1 and 6.

2. Turn my diagnosis steps into automated failure tests. The commands I used to find these bugs are the prevention: restart Postgres, pause Postgres, stop Redis, and assert that the API stays up and answers within 5 seconds. Run them in CI on every change to the API or compose files. They catch findings 2, 3 and 4, and any future code that adds a new dependency without handling its failure.

3. Make resilience a written standard, not something individuals have to remember. It goes in the review checklist and the service template:

  • Every network client (database, cache, HTTP) has an explicit timeout, shorter than the proxy's.
  • Every connection pool and client has an error handler.
  • Calls the response doesn't need never block the response.
  • Every service has a healthcheck, and dependencies wait for service_healthy. In Kubernetes, this becomes separate readiness and liveness probes.
  • Ports and hostnames come from a single variable. The API reads PORT from the environment, and nginx gets the same value through the image's built-in template support (/etc/nginx/templates + envsubst), so the two can't drift apart again.

Beyond this exercise, in a real production setup I'd also run at least two API instances behind nginx, so one crash isn't an outage. I'd also set nginx's proxy timeouts explicitly instead of relying on defaults, and practise database failover on a schedule. If you use a managed database, failovers will happen; the only question is whether you've tested them.

Observed, not addressed

I kept the scope to what makes the API stable. These came up during the investigation, and I'd raise them separately:

  • nginx caches the API's IP at startup. If the API container is recreated with a new IP, nginx keeps sending traffic to the old one until it's reloaded. I recreated the API several times and couldn't reproduce it, because Docker reused the IP, so this is a risk, not a confirmed bug. The fix would be resolver 127.0.0.11 with the upstream in a variable, or reloading nginx on deploy.
  • postgres/init.sql is never mounted. It sets max_connections = 20, but the live value is 100. If it were mounted, 20 would leave very little headroom once the API runs more than one instance at 10 connections each. Also, ALTER SYSTEM only takes effect after a restart. Someone should decide whether it's meant to be used.
  • Credentials are hardcoded (postgres/postgres in both compose and code) and .env is empty. In production these come from a secrets manager.
  • The API returns raw error messages to clients (err.message). That's useful for debugging, but it leaks internal details. In production I'd log the detail and return a generic message with a request ID.
  • Postgres has no volume, so its data disappears when the container is recreated. That doesn't matter for SELECT NOW(), but it would for a real service.
  • Minor: the empty nginx/nginx.conf should be deleted or mounted, and the obsolete version: key in the compose file can be removed.

docker compose stop redis; curl.exe -s -w " %{http_code} after %{time_total}s\n" http://localhost:8080/api/users; docker compose start redis

To see the "before" behaviour, run git stash, rebuild, and repeat the same checks, then run git stash pop.
